# Phase 0 — 可行性证伪工作包

> **目的**: 在写任何 Phase 1 工程之前, 用 1 周时间验证 [design v3 §1](../skill-harvester-design-v3.md#1-系统成立的前置假设v3-增补) 的 7 个前置假设。任何一个假设证伪 → 改方向, 不要继续往下烧钱。

这一份工作包**不是软件**, 是一份**带评分脚本的实验流程**。你只需要一份 YAML 数据文件 + 一个 Python 脚本就能跑完整轮验证。

---

## 文件清单

```
phase0/
├── README.md            ← 你正在读的, 执行指南
├── data.example.yaml    ← 数据收集模板 (示例数据已填好作为参考)
├── verify.py            ← 评分脚本, 读 data.yaml → 输出每个假设的 PASS/FAIL
└── data.yaml            ← 你创建的真实数据 (cp data.example.yaml data.yaml)
```

---

## 7 个假设速查

| ID | 一句话假设 | 通过标准 | 不通过的备选方案 |
|---|---|---|---|
| **A1** | 员工能写出动宾结构的日常任务清单 | 5-15 项 + 含 other + 评估者主观无空泛 + 自评覆盖 ≥80% | 工作太碎片化, 换目标用户 |
| **A2** | LLM 能在小样本下做高置信度 goal 分类 | top-1 ≥70%, 高置信度子集 ≥90% 且占比 ≥50% | 加视觉信号; 再不行退回每条都问 goal |
| **A3a** | immediate 层 0-30s 一句话快问能拿到瞬时记忆 | 自愿触发率 ≥10% + 平均信息量 ≥3/5 | immediate 档作废, 只剩 close-window |
| **A3b** | deferred 对比追问不依赖瞬时记忆 | 平均信息量 ≥3/5 + "记不清"比例 <30% | 缩短到 close-window 时延 |
| **A4** | 5-10 条同类 episode 能归纳可信规则 | 至少 1 条规则被另一名同岗位员工认可且能指出具体不准确点 | 等待更大样本量 |
| **A5** | SKILL.md 让 Agent 一致率显著提升 | 有 skill 组 vs 无 skill 组绝对差距 ≥ 20pp | 中间表示选错, 换格式 |
| **A6** | routine confirmation 触发器能在不打扰前提下抓到已压实产生式 | 1 周内至少 1 个高频候选 + 员工能给出可用规则陈述 | sensor B 路径作废, 只剩 sensor A |

详细标准见 design v3 §1 和 verify.py 顶部的 `THRESHOLDS` 字典。

---

## 7 天执行节奏(建议)

| 天 | 上午 | 下午 |
|---|---|---|
| **Day 1 (周一)** | 选目标员工, 启动 Betriebsrat 协议草案准备 | **A1**: 让员工花 30-45 分钟写日常任务清单 (对着真实日历/邮件) |
| **Day 2 (周二)** | 员工正常工作半天, 你在旁边按热键标记"困难瞬间", 收集 20 条 episode | **A3a**: 现场用物理按钮做 0-30s 一句话快问 |
| **Day 3 (周三)** | **A2**: 写一段 prompt, 用真 LLM 对 Day 2 的 20 条 episode 做 goal 分类, 让员工标 ground truth, 算指标 | **A6**: 让员工回看 Day 2 一天, 标出"今天我做了 N 次几乎一样的事"的高频项 |
| **Day 4 (周四)** | **A3b**: 当晚批处理 Day 2 的 episode, 用对比追问追 5-10 条 | 你扮演 L4, 对 A3a/A3b 的产物做手工归纳, 写出 3-5 条候选规则 |
| **Day 5 (周五)** | **A4**: 把候选规则拿给另一名同岗位员工 review | **A5**: 把规则手写成一份 SKILL.md, 准备 10 个新案例做 A/B |
| **Day 6 (周六)** | **A5**: 真跑 A/B —— 一个 LLM Agent 用 SKILL.md, 一个不用, 和原专家判断对照 | 把所有数据填进 `data.yaml` |
| **Day 7 (周日)** | `python verify.py` → 看 PASS/FAIL 报告 | 写 Phase 0 结论备忘, 决定 go / no-go / pivot |

## 怎么跑

```bash
cd phase0/
cp data.example.yaml data.yaml
# 编辑 data.yaml, 把示例数据替换成你的真实观测
python verify.py

# 想看每个假设的细节:
python verify.py --verbose

# 只跑某一个假设:
python verify.py --only A2
```

## 重要原则

1. **不要跳过任何一个假设**。它们之间不是"或"的关系, 是"且"。任何一个 fail 都意味着 v3 设计的某一段失效, 必须正面回应。
2. **不要为了让脚本绿就调宽阈值**。阈值来自 design v3 §1 的认知科学论证, 调宽 = 自欺欺人。
3. **PASS 不代表"做出来一定有用"**。它只代表"这个方向值得投资 Phase 1 的工程"。Phase 1 末尾还有一次端到端验收。
4. **FAIL 不代表"项目死了"**。看备选方案, 大部分 fail 都有 graceful degrade 路径。

## Phase 0 完成后

把 `data.yaml` 和 `verify.py` 的输出截图提交到 [`../CHANGELOG.md`](../CHANGELOG.md), 作为 v3 → v4 的输入证据。

如果全部 PASS, 跳到 [README](../README.md) 的 Phase 1 入口开始写代码。

如果有 FAIL, **不要**直接开始 Phase 1。先在 CHANGELOG.md 顶部新建一个 v3.1 章节, 把失败的假设和你打算的应对方案写进去, 让下一个接手的人能看到决策过程。
